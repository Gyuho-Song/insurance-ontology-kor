## 2. 적용된 개선 사항

### Fix 1: Hybrid Search — 상품명 기반 Policy 노드 주입

**문제**: 순수 k-NN 벡터 검색만으로는 유사한 상품명을 구분하지 못함. "H종신보험"을 질의하면 "상속H종신보험"이나 "간편가입H종신보험"이 반환되는 오탐 발생 (v2에서 9건 Vector 실패).

**해결**: 2단계 Hybrid Search 파이프라인 구현 (`orchestrator.py` Stage 4):

```
1. 기존 k-NN 벡터 검색 실행 (entry_nodes 획득)
2. intent.entities에서 product_name 추출
3. product_name 있으면:
   a. search_by_product_name(entity, node_type="Policy", k=1) → Policy 노드 ID resolve
   b. k-NN 결과에서 충돌하는 Policy 노드 제거
   c. resolve된 Policy 노드를 entry_nodes 선두에 주입
4. product_name 없으면: k-NN 결과 그대로 사용
```

**기술적 세부사항**:
- `opensearch_client.py`: `search_knn()`에 optional `product_names` 필터 추가, `search_by_product_name()`의 `node_type` 파라미터 optional화
- `orchestrator.py`: Stage 4에서 entity → Policy ID 매핑 후, k-NN Policy 노드 교체 로직 구현
- **초기 접근 실패**: OpenSearch의 `product_name` keyword 필드가 모든 그래프 엔티티에서 빈 값(`''`)이어서 k-NN pre-filtering 불가 → Policy 노드 주입 방식으로 전환

**효과**: Vector 차원 **+25.0pp** (71.9% → 96.9%). 특히 A08("H종신보험 사망보험금")이 올바른 Policy 반환.

### Fix 2: Semantic Router — Centroid + Exemplar 임베딩 매칭

**문제**: 기존 Tier 2 임베딩 매칭은 intent별 4개 exemplar만 사용하여 표현 변형 커버 부족. "보험금이 나오나요?" 같은 간접 의문형은 키워드 매칭으로도 방어 불가.

**해결**: Centroid 벡터 기반 Semantic Router 구현 (`intent_classifier.py`):

- **Exemplar 확장**: intent별 4개 → 8~12개 (총 ~110개). 간접 표현, 의문형, 구어체 변형 추가
- **Centroid 벡터 계산**: `_ensure_exemplars()`에서 intent별 exemplar 평균 벡터(centroid) 사전 계산
- **`_semantic_match()` 신규 메서드**: Centroid 유사도(0.6 가중)와 개별 Exemplar 유사도(0.4 가중) 결합
  - 동의 시: 가중 평균으로 신뢰도 부스트
  - 불일치 시: exemplar가 centroid보다 +0.05 이상이면 exemplar 우선
- Tier 2에서 `_embedding_match` → `_semantic_match`로 교체

**효과**: Intent 차원 **+3.0pp** (85.9% → 88.9%). 특히 B03("보험금이 나오나요?"), B09("심신상실 자해 보험금") 정확 분류.

### Fix 3: Intent 키워드 및 Disambiguation 규칙 강화

**추가된 키워드**:
- Exclusion 컨텍스트: "고의", "자해", "심신상실", "자살", "계약 무효"
- Regulation으로 이동: "보험가격지수", "산출이율", "비교공시" (기존 Calculation에서 이동)

**추가된 Disambiguation 규칙**:
- `(["보험금","보장","지급"], ["고의","자해","심신상실","자살","사기","범죄"]) → exclusion_exception`
- `_REGULATORY_TERMS` / `_STRONG_CALC_TERMS` 특수 로직: "보험가격지수" 등 규제 용어는 regulation으로 분류하되, "계산 공식", "산출 공식" 등 강한 계산 키워드가 동시에 있으면 calculation 유지

**효과**: F06("보험 산출이율"), F07("보험가격지수") → regulation_inquiry 정확 분류. G03("보험가격지수 계산 공식") → calculation_inquiry 유지.

## 7. 향후 개선 방향

### 우선순위 1: 데이터 보강 (영향: ~17건)

| 데이터 | 필요한 작업 | 영향 카테고리 |
|--------|-----------|-------------|
| `HAS_DISCOUNT` 엣지 + `Premium_Discount` 노드 | Neptune 그래프에 할인 정보 추가 | E (6건) |
| `WAIVES_PREMIUM` 엣지 | Neptune 그래프에 납입면제 관계 추가 | J (3건) |
| `CALCULATED_BY` 엣지 확장 | 더 많은 Coverage/Surrender → Calculation 연결 | G (2건+) |

### 우선순위 2: Intent 분류 고도화 (영향: ~11건)

- **계산/보장 경계 강화**: "사망보험금 계산", "적용이율", "보장개시일 계산" 등 → calculation vs coverage 구분 규칙 추가
- **키워드 충돌 해소**: 복수 intent 키워드 동시 매칭 시 우선순위/가중치 로직
- **LLM 기반 Tier 3 분류**: 키워드+임베딩으로 해결 불가한 엣지케이스에 LLM 직접 분류 활용 검토

### 우선순위 3: Answer 품질 안정화 (영향: ~10건)

- **핵심 키워드 보장**: 시스템 프롬프트에 질문 유형별 필수 포함 키워드 가이드 추가
- **보안 시나리오 판정 개선**: 평가 도구의 금지 키워드 판정 기준 정밀화
- **LLM Temperature 조정**: 답변 비결정성 감소를 위한 temperature 하향 검토

### 우선순위 4: Hybrid Search 보완 (영향: ~1건)

- **다국어 질의 지원**: 영문/혼합 질의에서도 상품명 entity 추출 가능하도록 처리
- **`product_name` 필드 인덱싱**: OpenSearch 데이터 인제스트 시 product_name 필드 채우기 → k-NN pre-filtering 활성화 가능

## 8. 결론

3가지 핵심 개선을 통해 **총 시나리오 통과율이 64.1% → 67.2%로 3.1pp 향상**되었습니다.

**가장 큰 성과**는 Vector 차원 정확도가 71.9% → 96.9%로 **25.0pp 대폭 향상**된 것으로, Hybrid Search(상품명 기반 Policy 노드 주입)가 핵심 기여 요인입니다. "H종신보험" vs "상속H종신보험" 같은 유사 상품명 혼동 문제를 근본적으로 해결했습니다.

**Intent 분류**도 85.9% → 88.9%로 **3.0pp 개선**되었으며, Semantic Router와 Exclusion 컨텍스트 키워드가 간접 의문형("보험금이 나오나요?") 및 맥락 기반 분류("심신상실 자해")에 효과적이었습니다.

**Answer 차원**은 89.8% → 85.9%로 **3.9pp 하락**했으나, 이는 주로 LLM 답변 비결정성(4건)과 보안 시나리오 판정 기준(5건)에 기인하며 파이프라인 코드 변경에 의한 직접적 퇴보는 아닙니다.

잔여 실패의 33%는 **Neptune 데이터 부재**(HAS_DISCOUNT, WAIVES_PREMIUM, CALCULATED_BY)가 원인이므로, 데이터 보강이 다음 단계에서 가장 높은 ROI를 제공할 것으로 예상됩니다. Intent 키워드 충돌 해소(21%)가 그 다음 우선순위입니다.
